# F01 fixed Pod admission proof

This versioned preparation copy targets Kubernetes1.36.1 on the dedicated ARM64 kind node with containerd2.3.1/LinuxKit7.0.14/Debian13 and already-qualified runsc systrap. Only the adapted admission entrypoint is proposed here; use its fixed explicit kubectl/crictl clients as root inside the node. The original K3s provisioning/transport instructions below document the maintained predecessor and are not executable instructions for this kind target. No native current-target admission/resource/network result is claimed.

This is a finite deployment-boundary fixture, not a runner, controller, production launcher or full F01 acceptance. It admits one fixed synthetic BusyBox Pod, rejects the checked-in mutation matrix, observes one live gVisor execution and removes that Pod and its scratch. It makes no identity, CSI, private-ingress, network-path, resource-stress or application-readiness claim.

`versions.yaml` records the measured ARM64 substrate. The driver measures and checks the exact node kernel/OS/containerd/K3s matrix, installed runsc release, configured systrap platform, Calico reported version and frozen OpenAPI inventory. A live Sentry process must also use systrap. These observations are provenance, not cryptographic attestation. Other versions, architectures, kernels and runtime/CNI combinations need their own review and real execution. The fixed BusyBox digest must already be present; `imagePullPolicy: Never` prevents test-driven downloads.

Run only inside an otherwise dedicated disposable Linux guest with K3s, runsc/systrap and Calico 3.33 already installed and healthy. The operator needs guest sudo and existing `bash`, `jq`, GNU coreutils and `findmnt`. Provisioning those prerequisites is outside this fixture. Do not export kubeconfig, mount host directories, import SSH agents or use an existing workload cluster. Keep at least 1 GiB guest disk free and an appropriate host reserve.

```sh
timeout 240 ./run-admission.sh /var/tmp/f01-evidence-001
```

Use a new absolute output directory outside the source checkout, ignored by any surrounding repository. The driver uses only guest-local `sudo k3s kubectl`/`crictl` and filesystem observations. It refuses existing Pods in `ilm-sandbox`. For the eight fixed namespace/SA/quota/network/RuntimeClass/policy/binding objects, it creates missing objects and refuses any pre-existing authority-relevant drift. It compares complete objects against resourceVersion-pinned server dry-run replacements, ignoring only status and known server metadata; namespace labels and top-level SA/RuntimeClass fields remain compared. Known namespace finalizer defaulting is explicit. No client-side apply merge or enforcement deletion is used. Review a differing task object and replace it explicitly before running; the driver leaves the verified floor installed. It never deletes the namespace, policy, binding or unrelated workloads. A temporary `f01-rejected-runc` RuntimeClass exists only to make the ordinary-handler negative reach CEL instead of failing RuntimeClass lookup; no Pod using it is launched, and it is deleted on exit. Pre-existing objects with that negative-only name cause refusal.

The floor permits exactly one named app container with a fixed image, command and arguments, UID/GID 65532, no token or free environment, no extra execution/volume/host surfaces, read-only root, no capabilities/escalation and RuntimeDefault seccomp. A single 16 MiB memory emptyDir with no mode override backs both `/scratch` and `/tmp`; this avoids gVisor's implicit writable `/tmp`. The fixed Pod has a 27-second deadline and a 120-second bounded idle interval for API observations. Container limits are 500m CPU and 256 MiB memory; requests and ephemeral-storage quantities are fixed. These declarations and OCI observations do not prove behavioral resource ceilings or a universal writable-byte limit.

The binding selects the control-plane-owned namespace label `kubernetes.io/metadata.name=ilm-sandbox`; removing the Pod profile label cannot skip it. CREATE and UPDATE of Pods, `pods/ephemeralcontainers` and `pods/resize` are matched. Both mutation subresources are denied; Pod status updates are excluded. Known server defaults are constrained. The initial CREATE accepts no annotations. On main-resource CREATE/UPDATE, extra labels, annotations, owner references and finalizers are rejected; existing supported annotations must be preserved exactly on UPDATE, with no principal exception. These assertions do not cover `pods/status`. The observed `calico` managed-fields manager writes the three CNI annotations through `status`; that manager string is not an authenticated request identity. The driver separately authenticates the configured CNI credential as `system:serviceaccount:kube-system:calico-cni-plugin` and checks its effective pods/status patch authorization plus selected Pod RBAC rules, without retaining its token or kubeconfig. No event audit proves the principal of the earlier write. Calico CNI and kubelet/node principals with status access remain trusted metadata writers. Kubernetes resets PodSpec on the status route; the metadata allowlist is not a status policy. Review `admission/v1/field-inventory.md` and its machine-readable inventory with the policy when updating the profile.

`failurePolicy: Fail` and binding `Deny` reject failed/evaluation-error requests while the guard is present. They do not keep enforcement present after policy/binding deletion or namespace drift. Production activation and context release still require an authoritative platform floor and real missing-enforcement transition tests through the future controller/Core. This fixture does not simulate those services or report a readiness pass. Future Job admission and workload RBAC remain separate obligations; operator-level fixture access is not controller RBAC evidence.

The driver records the exact source hashes, rendered/defaulted baseline, effective floor objects, policy generation/type warnings, case results and safe evidence hashes. CREATE negatives use server dry-run while the Pod is absent. UPDATE and subresource negatives use the live Pod's current resourceVersion. Success requires the exact expected rejection layer and fixed reason from `cases.tsv`; schema errors, missing RuntimeClasses, immutable-field errors, transport failures, CEL evaluation errors and unexpected accepts fail. PSA is explicitly expected for its shared security restrictions. Before cluster mutation, the driver requires exactly 59 unique case IDs, a one-to-one fixture mapping and a complete TSV final line. The policy-loaded check needs both allowed and exact denied dry-runs. The quantity control records the admitted canonical representation of `0.5` CPU and `268435456` bytes; API canonicalization means it does not isolate each CEL quantity comparison.

The separate `scratch-mode` control submits mode 493 and requires an accepted response with mode absent (`API_PRUNED`), because EmptyDirVolumeMode is disabled in this measured variant. The CEL guard also requires mode absent. Enabled-mode denial remains `UNEXECUTED`; this matrix refuses an enabled-gate result until separately reviewed, and never enables that alpha feature.

The live positive requires gVisor startup evidence and actual systrap process arguments, non-root/token/root/scratch markers and safe OCI fields. gVisor exposes the emptyDir through 9p inside the sandbox, so the 16 MiB backing is checked using the exact kubelet tmpfs mountpoint and both OCI mount sources. Dry-runs must leave the live spec/UID unchanged. Cleanup verifies Pod absence, disappearance of its exact kubelet scratch path and negative-only RuntimeClass absence. A main-resource unchanged UPDATE also has to be admitted after normal CNI status annotation writes. A failed prerequisite or earlier case leaves remaining required observations `UNEXECUTED` and returns nonzero; no arbitrary nonzero API result counts as a denial pass.

Create ownership is recorded only after a successful response. An ambiguous create timeout can leave a bounded fixed Pod or negative-only class; the run fails and the next run refuses it. The driver does not blindly delete an object that could belong to another invocation. Do not run concurrent proofs in this dedicated guest.

Inspect `results.tsv`, `sources.sha256`, `evidence.sha256` and the referenced outputs. Full F01 and every out-of-scope obligation remain `UNEXECUTED` regardless of this driver's exit status. Numeric line/condition coverage is not applicable to YAML/docs, and no zero-denominator coverage pass is claimed. The fixture driver's real positive/negative executions are functional evidence, not production-code coverage. New production application code must meet its independent quality gates.
